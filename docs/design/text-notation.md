# Text Notation / 独自記法パーサ仕様

> 対象: Editor のプレーンテキスト本文をどう HTML に変換するか（ルビ・傍点記法のパーサ仕様、セキュリティ、実装配置）。
> 正典は PRD §11。[frontend.md](./frontend.md) §4.2 の詳細版。データは [data-model.md](./data-model.md) `episodes.body` / `episode_revisions.body`（プレーンテキストの確定内容・スナップショット）を前提とする。

## サマリー

- 対応記法は 2 つ: ルビ `｜文章《ルビ》` → `<ruby>文章<rt>ルビ</rt></ruby>`、傍点(強調) `《《文章》》` → `<em class="emphasis-dots">文章</em>`（`text-emphasis` で装飾）。全角の `｜《》` のみを記法として認識し、半角 `|<>` はリテラル文字として扱う（自動判定はしない）。
- なろう/カクヨム流の「縦棒省略時に直前の漢字連続へ自動ルビ」は**採用する**。判定規則は「直前に空白・記号・改行を挟まず連続する漢字（CJK統合漢字＋々〆ヶ等の踊り字含む）の最大連続」を対象にする。
- 文法は EBNF で定義し、優先順位は「傍点 `《《…》》` を先に確定 → 残りに対して自動/明示ルビ」の 2 パス方式。エスケープは `《` の直前にバックスラッシュ `\《` を置く（リテラル出力は `《`）。未閉じ・不正記法は**変換せずリテラルとして残す**（フェイルセーフ、例外を投げない）。
- セキュリティは「**先に HTML エスケープ → その後に記法トークンを安全なタグへ置換**」の順序を必ず守る。記法変換は事前定義した固定タグ（`ruby`/`rt`/`em`）のみを生成し、属性値はユーザー入力から一切組み立てない設計にすることで XSS 経路を塞ぐ。
- 実装は `app/src/shared/text-notation/`（ドメインに依存しない純粋関数）に切り出し、SSR 本文レンダリングと Editor Preview island の**両方から同一関数を import** して使う。入出力は `renderNovelText(input: string): string`（HTML string）を主API とし、AST 中間表現は内部実装詳細として公開しない。

---

## 1. スコープと前提

- 対象は Episode 本文（`episodes.body` / `episode_revisions.body`）。タイトル・あらすじ等のメタ文言には適用しない（PRD §11 は Editor 本文の記法として定義されているため）。
- Editor は **Markdown ではなくプレーンテキスト**（PRD §11.1, [frontend.md](./frontend.md) §5）。ユーザーが直接入力するのは以下 2 種の記法のみ。
- 変換は「表示時（Read Path）」に行う。保存する `body` は常に生のプレーンテキストであり、HTML 化した結果を DB に保存しない（Revision 復元・再エクスポート・記法仕様変更時の再レンダリングを容易にするため）。

## 2. 対応記法

### 2.1 ルビ

```text
｜文章《ルビ》
```

変換後:

```html
<ruby>文章<rt>ルビ</rt></ruby>
```

- 区切り記号は**全角**のみを記法として認識する: `｜`（U+FF5C FULLWIDTH VERTICAL LINE）、`《`（U+300A）、`》`（U+300B）。
- 半角 `|`、`<`、`>` は記法として解釈せず、そのまま出力する文字（ただし HTML エスケープの結果 `<`/`>` は `&lt;`/`&gt;` になる）。
  - 決定 / 理由 / 代替案: なろう系サイトも全角 `｜《》` を採用しており、日本語文章中に半角記号が地の文で出現する頻度は低くない（会話文中の記号引用や half-width 記法テストなど）ため、全角限定にして誤爆を避ける。代替として「半角も許容し前後が日本語文脈なら記法とみなす」も検討したが、判定が複雑化し予測可能性を損なうため不採用。

### 2.2 傍点（強調）

```text
《《文章》》
```

変換後（案）:

```html
<em class="emphasis-dots">文章</em>
```

CSS 側（`app/src/styles/globals.css` に追加想定）:

```css
.emphasis-dots {
  font-style: normal;
  -webkit-text-emphasis: filled sesame;
  text-emphasis: filled sesame;
  -webkit-text-emphasis-position: over right;
  text-emphasis-position: over right;
}
```

- `text-emphasis`（傍点=圏点）が第一候補。非対応ブラウザ向けのフォールバックとして下線 (`text-decoration: underline dotted`) 等は CSS 側の `@supports` で吸収し、本書では HTML/クラス名の責務のみを定める。
- タグは `em` を採用（意味的に強調であり、`span` より意味づけが明確）。決定 / 理由 / 代替案: `strong` は「重要度」の意味合いが強く傍点の「語調強調」とはずれるため不採用。`span` は意味を持たないため `em` を採用。

### 2.3 縦書き時の考慮

- 縦書き（`writing-mode: vertical-rl`、[frontend.md](./frontend.md) §4.1）でも `<ruby><rt>` はブラウザの縦書きルビレンダリングにネイティブ対応しており、追加のマークアップ変更は不要。
- `text-emphasis-position` は横書きでは `over`、縦書きでは `right` が慣例（日本語の圏点は縦書きで右側に打つ）。CSS で `:where([data-writing-mode="vertical"]) .emphasis-dots { text-emphasis-position: right; }` のように、テキスト側の HTML 生成とは独立に、Reader Settings の書字方向クラスと連動させる（本書では HTML 生成までを扱い、書字方向依存の CSS 分岐は frontend 側の責務とする）。

## 3. 自動ルビ（縦棒省略）

なろう/カクヨム系サイトの慣行に合わせ、**縦棒 `｜` を省略した場合、直前の「漢字連続」に対して自動的にルビ対象とみなす**。

```text
今日《きょう》は良い天気だ。
```

→

```html
<ruby>今日<rt>きょう</rt></ruby>は良い天気だ。
```

### 3.1 判定規則（漢字境界）

`《…》` の直前にある文字から逆方向に走査し、以下の**いずれにも該当しない**文字が連続する区間を「漢字連続」としてルビ対象にする。

- 対象とする文字クラス（Unicode）:
  - CJK統合漢字: `一-鿿`
  - CJK統合漢字拡張A: `㐀-䶿`
  - 踊り字・繰り返し記号: `々`(U+3005) `〆`(U+3006) `ヶ`(U+30F6)
- 境界（連続を止める）とみなす文字: ひらがな・カタカナ・英数字・全角/半角記号・句読点・空白・改行・絵文字・すでに `《`/`》`/`｜` 自体。
- 走査開始位置: `《` の直前の 1 文字から開始し、上記の対象文字クラスである限り左へ伸ばす。対象文字が 1 文字も見つからない場合（直前がひらがな等）は自動ルビ不成立とし、`《…》` はそのままリテラル文字列として出力する（後述 §5 の不正記法扱い）。
- 明示的な `｜` がある場合は、`｜` の直後から `《` 直前までを丸ごとルビ対象文字列とする（漢字判定はスキップ、任意の文字列にルビを振れる）。これは名前・外来語へのルビ用途（例: `｜Alice《アリス》`）を許容するため。

### 3.2 なぜ採用するか

- 決定: 自動ルビ（縦棒省略）を採用する。
- 理由: PRD §11.2 は明示記法 `｜文章《ルビ》` のみを定義しているが、なろう/カクヨム利用者の執筆習慣との親和性が高く、単純な熟語へのルビ付けで `｜` の入力を省ける UX 向上が大きい。仕様としても「直前の漢字連続」という機械的規則で曖昧さを排除でき、実装コストも正規表現 1 本程度で収まる。
- 代替案: 「常に `｜` 必須」（シンプルだが移行者の執筆体験を損なう）、「形態素解析で単語境界を判定」（精度は上がるが依存重量・非決定性が増し PRD の "Writing Should Be Invisible" 原則から見て過剰）。いずれも不採用。

## 4. 文法定義（EBNF 風）

トークン化は文字列全体に対して左から右へ 1 パスで走査する。優先順位は「傍点を先に確定 → 残りに対しルビ規則を適用」。

```ebnf
document      = { segment } ;
segment       = escape | emphasis | ruby | plain-char ;

escape        = "\" , ( "《" | "》" | "｜" | "\" ) ;
                (* バックスラッシュ直後の記法文字1個をリテラルとして出力し、\ 自体は消費される *)

emphasis      = "《《" , emphasis-body , "》》" ;
emphasis-body = { any-char - "》" } ;
                (* "》》" が現れるまでを本文とする。ネストする "《《" はネスト扱いせず、
                   最初に閉じる "》》" で確定する（下記 §5.2）。空文字列（《《》》）は
                   本文長 0 として許容し、レンダリング結果は <em class="emphasis-dots"></em> *)

ruby          = explicit-ruby | auto-ruby ;
explicit-ruby = "｜" , ruby-base , "《" , ruby-text , "》" ;
ruby-base     = { any-char - ( "《" | "｜" | "\n" ) } ;
ruby-text     = { any-char - "》" } ;

auto-ruby     = kanji-run , "《" , ruby-text , "》" ;
kanji-run     = kanji-char , { kanji-char } ;
kanji-char    = ? Unicode 一-鿿 | 㐀-䶿 | 々 | 〆 | ヶ ? ;

plain-char    = ? 上記いずれにも一致しない任意の1文字（改行含む） ? ;
```

補足:
- `ruby-base` / `ruby-text` / `emphasis-body` はいずれも**空でもよい**が、`ruby-text`（読み）が空の場合は無効な記法とみなしリテラル扱いにする（読みのないルビは無意味なため。§5.1 で詳述）。
- `ruby-base` に改行を含めない（1 行内で完結する記法とし、複数行にまたがる誤爆を防ぐ）。`emphasis-body` は改行を許容する（傍点は文中の一区切りに使われ、複数文にまたがるケースはまれだが安全側で許容）。
  - 未決事項参照: emphasis-body の改行許容は要検討。

## 5. エスケープ・不正記法・優先順位

### 5.1 エスケープ

- `《` をリテラルとして出したい場合は `\《` と書く。同様に `》`・`｜`・`\` 自身もエスケープ可能（`\》` `\｜` `\\`）。
- バックスラッシュ自体は記法用の予約文字だが、上記 4 文字の直前以外では**通常の文字としてそのまま出力**する（例: `C:\path` の `\p` は「エスケープ対象文字でない」ため `\` も `p` もそのまま出力）。誤って全ての `\` を消費しないよう、エスケープはホワイトリスト方式にする。

### 5.2 入れ子・優先順位

- 傍点 `《《…》》` とルビ `《…》` は同じ `《` `》` を使うため衝突しうる。優先順位は次の通り決定する。

  1. まず文字列全体を左から走査し、`《《` が出現した位置を「傍点開始候補」として記録する。
  2. その直後に対応する `》》`（同じ深さで最初に見つかる `》》`）が見つかれば、その区間を傍点として確定し、**内部は再帰的にルビ記法を解釈する**（傍点の中に明示ルビ `｜文章《ルビ》` を書けるが、傍点の中でさらに傍点をネストすることは不可＝内部の `《《`はプレーンな `《《` 2 文字として扱う）。
  3. `《《` の後に対応する `》》` が見つからない場合、傍点としては不成立とし、`《` を単独の 1 文字として扱い、通常のルビ規則（explicit-ruby / auto-ruby）の対象として再評価する。
  4. 傍点として確定しなかった残りの `《…》` ペアに対して、ルビ規則（§3, §4）を適用する。

- 決定 / 理由 / 代替案: 「傍点を先に確定→残りをルビとして解釈」という 2 パス方式を採用。理由は、傍点記法 `《《》》` はルビ記法 `《》` の入れ子として自然に表現でき、実装（正規表現 or 簡易 state machine）がシンプルになるため。代替案として「ルビを先に解釈し、傍点は別記号にする」も検討したが、PRD §11.3 が明示的に `《《文章》》` を指定しているため不採用。

### 5.3 未閉じ・不正記法のフェイルセーフ

以下はすべて**変換を行わず、元の文字列をそのまま（HTML エスケープ後の状態で）出力する**。パース中に例外は投げない。

| 状況 | 例 | 扱い |
|---|---|---|
| `｜` の後に `《` が来ない（EOF or 改行） | `｜文章のまま` | `｜` はリテラル文字として出力 |
| `《` が開いたまま文末に到達（`》` 無し） | `今日《きょう` | `《きょう` をリテラル出力（自動ルビ不成立） |
| `》` だけが単独で出現（対応する `《` なし） | `文章》` | `》` をリテラル出力 |
| `《《` が開いたまま `》》` に到達しない | `《《強調のまま` | `《《強調のまま` をリテラル出力 |
| ルビの読みが空 `《》` | `｜文章《》` | 記法不成立、`｜文章《》` をそのままリテラル出力 |
| 自動ルビ対象の漢字連続が 0 文字（直前がひらがな等） | `のむ《のむ》` | 記法不成立、`のむ《のむ》` をそのままリテラル出力 |
| ネストした傍点 (`《《《《x》》》》`) | — | 外側の `《《…》》` を 1 組の傍点として確定し、内部の `《《`/`》》` はプレーンな `《`×2 / `》`×2 として扱う（§5.2 のルール 2） |

この「壊れた記法は静かにリテラルへフォールバックする」方針により、パーサは**入力データに対して常に成功し、例外や部分的な HTML 破損を起こさない**（読者に生の記号が見える程度の劣化に留める）。

## 6. セキュリティ（最重要）

### 6.1 変換順序の原則

**必ず「① HTML エスケープ → ② 記法トークンの安全な要素への置換」の順序を守る。**

```text
plainText
  → [1] escapeHtml(plainText)     // & < > " ' をエンティティ化
  → [2] applyNotation(escapedText) // ｜《》 記法のみを対象タグへ置換
  → safeHtml
```

理由: 記法変換を先に行うと、ユーザーが記法の「読み」や「本文」部分に `<script>` 等の生 HTML を混入させた場合、後段の `escapeHtml` がタグごとエスケープしてしまい記法自体が壊れる、あるいは逆に実装順序を誤ると生タグがそのまま出力されエスケープが素通りする実装ミスを誘発しやすい。**先にエスケープを完了させておけば、記法変換フェーズで生成するタグ（`<ruby>` `<rt>` `<em>`）以外に HTML として解釈される文字列が入力側から一切生成され得ない**ことが構造的に保証される。

### 6.2 XSS 混入経路と防止

| 経路 | 具体例（攻撃入力） | 防止策 |
|---|---|---|
| ルビ本文・読みへのタグ注入 | `｜<script>alert(1)</script>《ルビ》` | ①で `<script>` は `&lt;script&gt;` にエスケープ済みのため、②の正規表現は `<` を含む文字列ではなくエスケープ後の文字列に対してマッチする。出力は `<ruby>&lt;script&gt;alert(1)&lt;/script&gt;<rt>ルビ</rt></ruby>` となり実行されない |
| 属性注入（class 等を外部から書き換え） | `｜文章《"><img src=x onerror=alert(1)>》` | 記法変換で生成するタグには**ユーザー入力を属性値として一切埋め込まない**（`class="emphasis-dots"` は固定リテラル）。読み・本文はすべてテキストノードとしてのみ挿入されるため、閉じクォート等での属性脱出は成立しない |
| URL/href の注入 | （本記法には該当箇所なし） | ルビ・傍点変換は `href`/`src` 等の属性を一切生成しない。リンク化は別機能（もしあれば）でホワイトリスト方式のURLサニタイズを別途行う |
| 二重変換によるエスケープ漏れ | Revision 復元時に既に HTML 化された文字列を再度 `applyNotation` に通す | **DB には常にプレーンテキストのみ保存し、HTML 化済み文字列を保存・再入力しない**（§1）。レンダリング関数は「プレーンテキスト→HTML」の一方向のみを提供し、HTML→HTML の再適用 API は公開しない |
| Unicode 正規化・全角/半角混同を利用した回避 | 半角 `<script>` に全角に見せかけた文字を混在させる 等 | 記法対象は全角 `｜《》` のみで、半角 `<>` 系はそもそも記法トリガーにならない。エスケープは Unicode 正規化前の生バイト列に対して行い、記法パーサは正規化を行わない（正規化による誤爆・回避の余地を作らない） |
| Preview island での二重実行 | Editor Preview で `renderNovelText` をクライアント側でも呼ぶ | SSR/Preview は**同一の純粋関数**を共有するため、エスケープ実装の食い違い（サーバ版は escape するがクライアント版はしない、等）が原理的に起きない（§7） |

### 6.3 実装上の禁止事項

- `dangerouslySetInnerHTML` 相当の生 HTML 差し込みは、`renderNovelText` の出力結果を **信頼済み HTML** として扱う 1 箇所（本文表示コンポーネント）に限定する。それ以外の場所でユーザー入力文字列を直接 `innerHTML` 相当に渡さない。
- 記法変換の正規表現・パーサは**タグを文字列結合で組み立てず**、テンプレート内の固定タグ文字列 + エスケープ済みテキストのみを差し込む形にする（属性値の動的生成をしない設計そのものが最大の防御）。
- タイトル・あらすじ・コメント等、本記法を適用しない他フィールドは、記法変換を通さず**エスケープのみ**で表示する（記法パーサを誤って適用しない）。

## 7. 実装配置

### 7.1 モジュール

```
app/src/shared/text-notation/
├ index.ts          … 公開API: renderNovelText()
├ escape.ts          … escapeHtml()
├ tokenizer.ts        … §4 の文法に基づくトークナイズ（内部専用）
├ render.ts           … トークン列 → HTML string
└ text-notation.test.ts
```

- 配置は `domain/writing/` ではなく `shared/` を採用する。
  - 決定 / 理由 / 代替案: 記法変換は「文字列 → 文字列（HTML）」の純粋な表示ロジックであり、Episode・Revision 等のドメインエンティティや Repository に依存しない。Reader（本文表示）・Writing（Editor Preview）の**両ドメインの Presentation 層から使われる**ため、特定ドメインの配下に置くと循環参照や不要な依存が生まれる。`shared/` に置くことで [architecture.md](./architecture.md) のレイヤ図における Domain 非依存のユーティリティとして扱える。
  - 代替案: `domain/writing/services/` に置き reading 側から import する案は、reading→writing への依存が生まれ「一方向依存」の原則（[architecture.md](./architecture.md) §2）を崩すため不採用。

### 7.2 公開 API（入出力の型）

```ts
// app/src/shared/text-notation/index.ts

/**
 * Episode本文のプレーンテキストを、ルビ・傍点記法を適用したHTML文字列へ変換する。
 * 事前にHTMLエスケープを行った上で記法を適用するため、戻り値は常に安全なHTMLとして
 * innerHTML相当の場所に挿入してよい。
 */
export function renderNovelText(input: string): string;
```

- 入力: `string`（プレーンテキスト、改行 `\n` を含む。改行から `<br>` / 段落分割への変換は本モジュールの責務外とし、呼び出し側の本文レンダリングコンポーネントが `renderNovelText` を行単位/段落単位に適用する形にする。もしくは改行を `\n` → `<br>` に変換する処理を `render.ts` 内に含めるかは未決事項参照）。
- 出力: `string`（安全な HTML 文字列）。呼び出し側でこれ以上のエスケープは行わない（二重エスケープ防止）。
- 内部で AST（トークン列）を経由するが、AST 型 (`NotationToken[]`) は `tokenizer.ts` 内に留め、外部には公開しない（実装の自由度を保つため。将来 Markdown 的な追加記法が増えても API 互換を維持できる）。

### 7.3 SSR / Editor Preview での共有

| 呼び出し元 | レイヤ | 用途 |
|---|---|---|
| `presentation/views/episode-view.tsx`（想定） | SSR View（hono/jsx） | Episode 本文表示。`renderNovelText(episode.body)` の結果を安全な HTML として挿入 |
| Editor Preview island（`hono/jsx/dom`） | Client island | 執筆中の本文をリアルタイムプレビュー。同じ `renderNovelText` を **バンドルして** クライアント側でも実行する（サーバ往復なしで即時反映） |

- 同一ロジックを共有するため、`shared/text-notation` は Node/Bun 双方・ブラウザバンドル双方で動く**純粋 TypeScript のみ**（Drizzle・Hono 型に依存しない）で実装する。これにより hono/jsx/dom 側のバンドルにそのまま含めても不要な依存を引き込まない。

## 9. 未決事項

- 改行の扱い: `renderNovelText` が `\n` → `<br>` 変換まで担うか、呼び出し側（段落分割コンポーネント）に委ねるかは未確定。現状案は「本モジュールは記法変換のみ担当し、改行/段落化は呼び出し側の責務」だが、Editor Preview と SSR で改行処理まで揃える必要があるため実装時に確定させる。
- `emphasis-body` に改行を許容するかどうか（§4 補足）。許容すると複数行にまたがる傍点が可能になるが、誤入力（閉じ忘れ）の影響範囲が広がるリスクがある。
- ルビの読み（`rt`）に記法（ネストしたルビや傍点）を許すか。現行案は「読み側は plain text 固定でネスト不可」を暗黙前提としているが、EBNF・テストケースには明記していない。実装時に `ruby-text` 内の `《`/`｜` の扱いを明文化する必要がある。
- 自動ルビの対象文字クラスに CJK拡張B以降（サロゲートペア文字）を含めるか。現行は BMP 内の `一-鿿` `㐀-䶿` のみを対象にしており、まれな拡張漢字（サロゲートペアが必要な文字）でのルビ振りは自動ルビの対象外になる（明示 `｜` を使えば回避可能）。
- パフォーマンス: 長大な Episode本文（数万文字）に対する正規表現ベースのトークナイズの計算量。バックトラッキングを避けた実装（線形走査の state machine）にするか、正規表現の組み合わせで十分かはベンチマーク未実施。
